dagron-ci is up once its database answers. Connect a repository:
{{- if eq (include "dagron.ci.inEnginePod" .) "true" }}
    kubectl -n {{ .Release.Namespace }} exec deploy/{{ include "dagron.fullname" . }}-engine -c dagron-ci -- dagron-ci repo add github.com/OWNER/NAME
{{- if eq (int .Values.engine.replicas) 0 }}
  ⚠  engine.replicas is 0, and dagron-ci runs in the engine's pod
     (ci.placement: engine): there is no dagron-ci until the engine has a
     replica. Nothing takes a webhook or looks for a commit meanwhile.
{{- end }}
{{- if not .Values.ci.checkoutTokenSecret.name }}
  No ci.checkoutTokenSecret: a private repository's checkout is given no
  credential, and fails. Make a secret for the engine to ask dagron-ci with:
       kubectl -n {{ .Release.Namespace }} create secret generic dagron-ci-checkout --from-literal=secret="$(openssl rand -hex 32)"
  Then name it to the chart: upgrade this release with the options it was
  installed with, and this one added to them:
       --set ci.checkoutTokenSecret.name=dagron-ci-checkout
{{- end }}
{{- else }}
    kubectl -n {{ .Release.Namespace }} exec deploy/{{ include "dagron.fullname" . }}-ci -- dagron-ci repo add github.com/OWNER/NAME
{{- if .Values.ci.checkoutTokenSecret.name }}
  ci.checkoutTokenSecret is named, and dagron-ci has a Deployment of its own
  (ci.placement: deployment): this release's engine is not told to ask it for
  a checkout's credential, and a private repository's checkout fails. In the
  engine's pod (ci.placement: engine) it is.
{{- end }}
{{- end }}
{{- if not .Values.ci.apiTokenSecret.name }}
  ⚠  ci.apiTokenSecret is not set, so events are taken and stay queued. Make an
     API token in the console, put it in a Secret, and name it and the
     dagron-api that runs go to, over TLS:
       --set ci.apiTokenSecret.name=<secret>
       --set-string ci.cells=default=https://<dagron-api, behind TLS>
{{- end }}
{{- if not .Values.ci.webhookSecret.name }}

Reach the UI:
{{- if .Values.ingress.enabled }}
  http{{ if .Values.ingress.tls.enabled }}s{{ end }}://{{ .Values.ingress.host }}/
  ( /api/* is routed to dagron-api on the same host so the session cookie works )
{{- else if .Values.frontend.enabled }}
  Ingress is disabled. Port-forward to try it locally:
    kubectl -n {{ .Release.Namespace }} port-forward svc/{{ include "dagron.fullname" . }}-frontend 3000:{{ .Values.frontend.port }}
    kubectl -n {{ .Release.Namespace }} port-forward svc/{{ include "dagron.fullname" . }}-api 8080:{{ .Values.dagronApi.port }}
  then open http://localhost:3000. Note: /api calls only work if the frontend is
  configured to reach dagron-api (port-forwarded above on :8080) — the clean
  same-origin setup is ingress.enabled with a host.
{{- else }}
  Ingress is disabled. dagron-api serves the console at / and the API under /api on
  the same origin, so one port-forward is enough:
    kubectl -n {{ .Release.Namespace }} port-forward svc/{{ include "dagron.fullname" . }}-api 8080:{{ .Values.dagronApi.port }}
  then open http://localhost:8080.
{{- end }}
